An on-device LLM against a rule-based reader

Eight real wine labels, Apple's Foundation Models framework, and a result I did not expect. 24 September 2026.

I write a small iPhone app called Decanted: a journal for the wine you drink. You photograph the label, and the app fills in producer, name, vintage, region, grapes and alcohol so you only have to correct what it got wrong. The text comes out of Apple's Vision framework on the device; nothing is uploaded, because the app has no server to upload it to.

Turning recognised text into fields is done by about three hundred lines of rules: regular expressions for the year and the alcohol, and lookups against bundled catalogs of grape varieties and wine places. It is unfashionable code. When iOS 26 shipped a language model that runs on the phone for free, the obvious question was whether the unfashionable code should go.

The label that started it

A user — me — photographed a bottle of Zinfandel and got nonsense: producer LODI-CALIFORNIP, wine FANDE. The label reads THINK BIG! GREAT ZINFANDEL, LODI-CALIFORNIA, VAT.66, in large stencilled capitals.

Running the same photograph through Vision with the app's settings — .accurate, language correction on — gives this, with the engine's own confidence per line:

0.30  GRLBSE          <- a shop sticker
0.50  Voini Wi        <- the same sticker
1.00  THINK BIG!
1.00  BREAT           <- GREAT
0.50  ZIN        ℿ
1.00  FANDEL     ⅀    <- one word, set across two lines
1.00  ODI-CALIFORNE   <- LODI-CALIFORNIA, misread at both ends
1.00  UAT.66          <- VAT.66

Vision did well. The rules did not, and for three reasons worth naming. "Zinfandel" is set so large that it wraps, and neither ZIN nor FANDEL is a grape on its own. LODI-CALIFORNIA is two places joined by a dash, misread at both ends, and Lodi was missing from the catalog anyway. And because neither the grape nor the place was recognised, both lines were left to the routine that guesses the producer and the name — which picks the largest type on the bottle. The largest type on the bottle was exactly those two lines.

Handing it to the model

Apple's Foundation Models framework gives you a few-billion-parameter model on the device, free, offline, with structured output. The whole integration is a struct and a prompt:

@Generable
struct LabelReading {
  @Guide(description: "The winery or producer. nil unless a line clearly names one.")
  var producer: String?
  @Guide(description: "Grape varieties, in standard spelling, joining words split over two lines.")
  var grapes: [String]
  @Guide(description: "The vintage year ONLY if four digits of a year appear. Otherwise nil.")
  var vintage: Int?
  // ...name, appellation, region, country
}

let session = LanguageModelSession(model: model, instructions: """
You correct what a camera read from a wine label. Letters are often misread
(BREAT is GREAT, CALIFORNIP is CALIFORNIA) and a word may be split over two lines
(ZIN then FANDEL is ZINFANDEL). Shop stickers and codes belong to no field.
Only report what the text supports. When unsure, answer nil. Never guess a year.
""")

Two practical notes before the results. The default guardrails refuse a certain amount of alcohol-related content, so a wine app wants SystemLanguageModel(guardrails: .permissiveContentTransformations). And the first runs were not reproducible until sampling was set to .greedy; the same label gave different answers on consecutive calls.

The first thing the model did, with an instruction in front of it saying never guess a year, was guess a year. The label carries no vintage at all. It returned 2022. On the next run, 2024. Greedy sampling and an optional field fixed that particular failure — but a plausible year nobody printed is exactly the kind of mistake a journal must not make, because a blank field is obvious and a wrong one is not.

Eight bottles

One label proves nothing, so I ran both readers over eight photographs of my own bottles — each one recognised by Vision first, so both approaches saw exactly the same text. The model ran on macOS 26.6, which carries the same on-device model as the phone.

Rules won four, the model won two, both failed one, and on the French label the model refused to answer at all — "Unsupported language" — which rules out a good share of the wine world.

The score is not the interesting part. The kind of error is. The rules fail by leaving a field empty: you see the gap and you fill it in. The model fails by being confident. "Rabago" and "Citran" are not grapes, they are a place and a château; nothing on either label suggests a variety, and the model supplied one anyway. Spätburgunder is the German name for Pinot Noir, and the model let the "burgunder" in it carry the bottle to Burgundy, France. A journal that quietly records a German wine as French is worse than one that records nothing.

What the model was right about

Both of its wins turned out to be my own gaps. Susumaniello was not in the grape catalog. Pays d'Oc was not in the places. The model knew them because it has read the internet; my catalog knew neither because I had written it by hand from memory. That is a fair criticism of the rules, and it is fixable with data rather than inference — so I fixed it: the catalogs went from 127 grape varieties to 206 with their local synonyms, and from 108 wine places to 434.

The three failures on the Zinfandel label were fixable too, and none of them needed a model:

  • Two adjacent single-word lines are now tried joined, so ZIN + FANDEL resolves to Zinfandel.
  • A line with a dash is resolved part by part, each part tolerant of a misread letter or two, so ODI-CALIFORNE still yields California.
  • A line the recogniser itself scored below 50% is no longer a candidate for the producer's name, which drops shop stickers — the exact thing the model fell for on two labels.

Lookups are now tolerant in general: one edit for words of five to eight characters, two beyond that, nothing below five, and a tie is refused rather than guessed. "Sauvignen Blanc" finds Sauvignon Blanc; "Gamza" does not become Gamay.

All eight labels are now fixtures in the test suite — Vision's own output, confidences and boxes included. Every future change to the reader is judged against real bottles instead of against strings I invented.

What this does and does not show

It does not show that language models are bad at reading labels. A large multimodal model, given the photograph rather than the recognised text, would almost certainly beat both of these readers; it would see the gold foil that Vision missed entirely. What it shows is narrower and, I think, more useful: the free model that runs on the phone today, on text a phone camera produced, was not better than a few hundred lines of rules and a good list — and it was worse in the way that costs a user most.

There is also the reason I did not reach for a cloud model, which is the same reason the app has no account: the photographs and the notes stay on the device. An on-device model was appealing precisely because it would not break that. It simply did not earn its place.

I will try it again when the model grows, and the benchmark is now sitting in the repository waiting for it. Until then the unfashionable code stays.

Decanted is free on the App Store — no account, no server, no ads. If it misreads a bottle you own, send the photograph to agnevstsikov@gmail.com; each label that fails becomes a test.
